# EditAnchored 下一轮优化（证据驱动）

本文取代同名的 AI 生成版本。原版的数据纪律可保留（见 §7 留档），但它的优先级排序与仓库口径不符，
且漏掉了两个收益更高的改动。**本文的每一条都来自本机真实调用数据的复核**，口径与复核脚本见 §1。

关联文档：

- `specs/edit-anchored-verification.md`：hashline 的权威设计记录与历轮缺陷复验，**改动语义以它为准**。
- `specs/edit-tool-roadmap.md`：整体路线与阶段划分。
- `scripts/analyze-edit-tools.mjs`：工具用量与失败分布统计入口。

## 1. 基线复核（2026-09-28）

### 1.1 口径

原版文档用 `ESTIMATED_TOKEN_CHAR_DIVISOR = 4` 估算 token，仓库实际是 **3**
（`packages/shared/src/usage-stats.ts`）。凡涉及工具定义 token 的绝对值，原版低估约 25%。
本文所有 token 数字用 `estimateTokens`（`core/context/utils.ts`）实测。

失败分类**以存储的 `state.error` 文案为准**，不按日志 `error.context.code`（实测两者不一致，
日志会把 `unserved` 记成 code 2 之外的值）。同时剔除测试造数：会话中出现 `ZZZZ`、`2CAP`、
`"abc"`、`not-an-anchor` 等人工锚点的调用不计入统计，否则会把自测流量当成真实缺陷。

### 1.2 实测结果

剔除造数后（`scripts/analyze-edit-tools.mjs` 输出，共剔除 66 个造数部件），
`EditAnchored` 共 **263 次调用 / 42 次失败 = 16.0%**（同口径下 `Edit` 为 8.3%）。按失败原因：

| 原因        | 次数 | 查询                                | 恢复代价（后续到同文件下一次编辑之间的其它工具调用） |
| ----------- | ---- | ----------------------------------- | ---------------------------------------------------- |
| `stale`     | 7    | 哈希不在当前文件                    | 0 次，但 4/7 恢复、3 放弃                            |
| `unserved`  | 13   | 哈希不在已读集合                    | **平均 4.69 次，累计 61 次额外调用**，最贵           |
| `ambiguous` | 9    | 哈希命中多行                        | 0.22 次                                              |
| `malformed` | 4    | 锚点格式不合法（实为裸哈希）        | 0 次（全部自愈）                                     |
| `schema`    | 4    | 入参未过 JSON Schema                | 0 次，但仅 1/4 恢复、3 放弃或换工具                  |
| `overlap`   | 3    | 编辑区间重叠                        | 0.67 次                                              |
| `reversed`  | 2    | `remove_from` 排在 `remove_to` 之后 | 1.50 次                                              |

关键结论：

1. **失败几乎都能一步自愈。** 除 `unserved` 与 `schema` 外，模型下一步就改对了。所以"缩短恢复"
   的收益很小，**真正的杠杆是"不要发生"**。原版把恢复成本当作主要论据，方向反了。
2. **`unserved` 是最贵的可修项**：13 次调用共产生 61 次额外工具调用，集中在 Read→Edit 的往返。
3. **`stale` 与 `schema` 的「放弃」值得注意**：这两类的额外调用数是 0，但分别只有 4/7 与 1/4
   在失败后继续编辑同一文件——计数为 0 不等于没代价，而是任务直接卡住了。单看「平均恢复代价」
   会把这两类误判为无需处理。

### 1.3 两个被漏掉的改动

原版把"裸哈希"列为 P0，理由是"实测只有 3 条"。按 `state.error` 复核后是 **4 次调用、17 个锚点**
（一次批量编辑里就有 13 个）。这 17 个哈希**全部是合法的、确实在已读集合里的哈希**，只是模型
省了 `行号:` 前缀（逐条核对过 `Read`/`Bash` 的上下文）。工具把"你少写了行号"报成了
"你的锚点是垃圾"，是**诊断错误**；而 4 次里有 4 次靠模型自己猜回正确写法才恢复。

另一个原版完全没提的项是 **`remove_to` 冗余**：成功调用的 307 个锚点编辑中，**49.8% 是
`remove_to === remove_from`**（单行编辑写了两遍同一锚点）。这个观察是对的，但把“省略
`remove_to`”做成改动会让多行编辑静默截断（详算见 §2.3），所以**评估后放弃**。

## 2. 产品规则

### 2.1 锚点三段式保持不变

锚点格式 `行号:4位哈希`，哈希由 `hashLineContent`（`anchor-hash.ts`）对**去掉行尾换行后的整行**
计算。哈希算法、字母表、归一化规则不改；`parseAnchor` 的严格模式不变。

### 2.2 新增：裸哈希（hash-only）作为合法简写

**规则**：`remove_from` / `remove_to` 允许只给 4 位哈希，省略 `行号:`。

解析优先级（`parseAnchor` 之后新增一层）：

1. 形如 `行号:哈希` → 现有严格解析，行为不变。
2. 形如 4 位哈希（可选大小写、`I/L/O/U` 归一化）→ **裸哈希**，按下列规则解析：
   - 在**当前文件**中唯一命中 → 解析为该行。
   - 命中多行 → `ambiguous`（与显式锚点多命中同一条路径，回传候选区域）。
   - 当前文件零命中但**该哈希在已读集合里** → `stale`（模型读过、文件已变）。
   - 当前文件零命中且**不在已读集合** → `unserved`。
3. 其它 → `malformed`。

**判别器收紧**（原版遗漏的风险）：裸哈希判定要求候选串是 4 位且字符集符合归一化后的字母表
（`0-9A-HJKMNP-TV-Z`，去掉 `I`/`L`/`O`/`U` 的歧义位）。纯 4 字母词如 `BOOK` 归一化后是 `B00K`，
其中 `0` 合法、整体合法，仍按裸哈希处理——这与显式锚点里 `B00K` 会被当哈希是**一致**的，
不引入新的误判面。但**长度不等于 4 或含字母表外字符**（如 `abc`、`not-an-anchor`、空串）
必须仍然报 `malformed`，不得退化成 `unserved`。

**为什么安全**：裸哈希只在**已读集合**或**当前文件唯一命中**时解析成功，二者都不放宽
「只允许改模型看过的行」这条门禁（`anchor-served.ts`）。零命中时仍然拒绝。

### 2.3 评估后放弃：`remove_to` 改为可选

**结论：不做。** 这是本轮唯一一个先实现、又根据数据回退的项，留在这里是为了避免以后
重复讨论。

一开始的理由看上去成立：成功调用的 307 个锚点编辑里 **49.8% 是单行编辑**，却把同一个锚点
抄了两遍（`remove_to === remove_from`）。但逐条核对失败后，这个理由站不住：

1. **它不能防任何失败。** 实测 5 个 `remove_to` 相关的失败**全部是真实多行区间上的
   `ambiguous`**（同一行内容在文件里出现多次），而 `ambiguous` 的根本原因是哈希区分度，
   不是写法冗长。省略 `remove_to` 不会减少一次拒绝。
2. **它还引入一个不可忽视的新风险。** 另有 **161 处真实多行编辑**，一旦模型漏写
   `remove_to`，工具会**只改一行、照样返回成功**——模型无从得知，用户看到的是一个
   “成功”但内容错的文件。与它相比，49.8% 的冗长是完全可以接受的代价：
   多余的写法只会被拒绝，漏写的范围会被静默截断。
3. 保留现状还能继续吃到 `reversed_range` 这道护栏（首尾颠倒会被报错）。

**保留的行为**：`remove_to` 在 schema 里仍为必填；但解析层对“留空串”、
“与 `remove_from` 写同一个锚点”这两种历史写法**继续当作单行编辑**，不因为这项评估而变成拒绝。
对应测试：`remove_to 留空时按单行处理`。

### 2.4 新增：`unserved` 也 reject-and-serve

**现状**：`stale` 与 `ambiguous` 会回传「Current anchors (lines X-Y)」区域，`unserved` 不渲染任何
内容（`anchor-resolve.ts` 的 `plain()` 分支），模型必须 `Read` 一次再重发，共 2 次往返。

**规则**：`unserved` 拒绝时，若模型给出了**行号**，则回传该行号附近区域（复用
`formatAnchorRegion` 与 `REGION_CONTEXT_LINES`）的当前锚点，与 `stale` 走同一渲染路径。

**必须同时满足的两条**（否则会复现 `edit-anchored-verification.md` §2 的回归）：

1. 回传区域内的锚点**必须写入已读集合**（走 `writeAnchoredReadState`），否则模型照抄回传的锚点
   会被再次判 `unserved`，比不渲染更糟。
2. **只写回传的那一小段区域**，不得写整文件。写整文件就是 §1 那条已修缺陷（"文件任意位置都能改"），
   会绕过 `Edit`/`Write` 的读门禁。`isPartialView` / `content` / `offset` / `limit` 等门禁字段
   保持现有语义，不因这条改动被重写。

**取舍**：这条**不削弱**门禁——渲染区域等于"把这几行给模型看"，模型随后编辑的正是看过的行。
它只把"拒绝 + 让模型自己 Read"换成"拒绝 + 直接把区域给它"。若模型没给行号（例如只给了垃圾串），
保持现有的 `plain()` 不渲染。

### 2.5 新增：工具描述里预置字段说明（而不改校验层）

实测 4 次 `schema` 失败**全部**是形状混用：3 次把 `Edit` 的 `old_string`/`new_string` 当成
本工具的字段（模型看到 `Edit` 名字相近就套用了），1 次传了空对象。

**规则**：这两类都得在**工具描述**里给出可照抄的形态，而不是在各处校验层里逐工具写适配——
`input-validation-model-content.ts` 与 `executor/validation.ts` 是**全工具共享**的基础设施，
在里面塞本工具专属措辞会破坏分层，而且 4 次失败已经全部自愈，不值得为大改。
已落地：描述顶部给最小可用示例（只带 `remove_from`），并显式声明 `remove_to` 可省、
裸哈希可省行号。

**验收**：新增/修改描述后，`estimateTokens` 记账表明**净增不超过 40 token**（本工具–
一次请求的固定成本），并在真机里观察 `schema` 类失败是否下降。若描述改动后仍有形状混用，
再考虑把回退提示加到执行器层，而不是一次性两处都改。

### 2.6 不做

- **不改哈希算法、不缩短哈希长度**：碰撞率是门禁的基础，见 `anchor-hash.ts` 注释。
- **不给 `EditAnchored` 加自动重试**：模型自己一步就能改对，服务端重试会掩盖真实错误。
- **不放宽 `unserved` 的零命中拒绝**：那是"改没看过的行"，是 `Edit`/`Write` 门禁的另一面。
- **`remove_to` 省略不做隐式范围推断**（见 §2.3 边界）。

## 3. 状态所有者与数据流

| 状态                     | 所有者                                | 说明                                                                            |
| ------------------------ | ------------------------------------- | ------------------------------------------------------------------------------- |
| 已读集合 `servedAnchors` | `readFileState`（按 `filePath` 一条） | 唯一写入路径 `writeAnchoredReadState`；`Read` 与拒绝回传都走它                  |
| 文件当前内容             | 每次调用重新读取                      | 不缓存，避免与外部改动竞争                                                      |
| 解析结果 `reason`        | `anchor-resolve.ts`                   | 单一判定点，`malformed` → `unserved` → `stale` → `ambiguous` 的**判定顺序固定** |

**判定顺序必须是**（顺序错会导致误报）：

```
1. 格式非法              → malformed    （不做任何集合查询）
2. 哈希不在已读集合       → unserved     （先查集合，后查文件）
3. 已读但文件里找不到     → stale
4. 文件里命中多行         → ambiguous
5. 命中一行             → 解析成功
```

第 2 步在第 3 步之前，是因为"模型没看过"比"文件变了"更根本；反过来会把没读过的哈希报成 `stale`，
给出"文件已变"的错误建议。§2.2 的裸哈希分支进入这张表的**第 1 步之后**，复用同一顺序。

**单行编辑的数据流**：`remove_to` 留空、或与 `remove_from` 写成同一个锚点时，
不解析末端，直接用 `remove_from` 解析出的索引作为区间两端（`singleLine` 分支），
后续重叠校验、应用、回归锚点渲染全部按单行区间走。

## 4. 接口

`EditAnchored` 入参（`apps/zcode-cli/packages/contracts/src/tools/edit-anchored.ts`）：

```ts
edits: Array<{
  remove_from: string; // 锚点；支持 "行号:哈希" 或裸哈希（唯一命中时）
  remove_to: string; // 区间末端锚点；单行编辑时与 remove_from 相同
  replacement_text: string; // 可以为空串（纯删除）
}>;
```

- `remove_to` **保持必填**（理由见 §2.3）。
- `remove_from` 的描述补一句：可省略行号只给 4 位哈希，将在当前文件唯一匹配时解析。

协议类型是共享面：同步更新 `packages/shared` 侧对应类型（若该 schema 由 `zod`/TS 类型生成，
以生成链为准），并提供**运行时校验**，不能只改类型。

## 7. 原版文档的处理留档

原版（AI 生成）的下列结论**经复核不成立**，已在本文修正：

| 原版结论                                 | 复核结果                                                                                              |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 裸哈希实测"只有 3 条"，收益最低          | 实为 4 次调用 / 17 个锚点，且**全部是合法已读哈希**，属错误诊断                                       |
| `anchor-resolve.ts` 431 行"已超架构上限" | `apps/zcode-cli` 是 `managed: false`，`maxFileLines` 不适用；全量 `architecture:check` violations = 0 |
| token 数字（30 928 等）                  | 用了 ÷4，仓库口径是 ÷3，绝对值低估约 25%                                                              |
| "失败恢复成本 1.6%，已进入收益递减区"    | 调用级失败率 16.0%，`unserved` 单类就产生 61 次额外调用；不是收益递减                                 |
