# 编辑工具使用情况分析（首轮，2026-09-24）

数据源：`~/.zcode/cli/db/db.sqlite` 的 `part` 表（工具调用与状态）、`~/.zcode/cli/log/zcode-*.jsonl`（`tool.call.failed` 的原因码与消息）。

口径说明：已安装的 ZCode Preview 含主备切换（`default way to edit a file you have already read`、`after two EditAnchored failures` 两段文本在包内），所以 09-23 之后的数据反映切换后的行为。`EditAnchored` 于 09-22 才引入，早于此的 `Edit` 数据不参与对比。

## 1. 调用比：切换生效了

| 日期  | EditAnchored | Edit | EditAnchored 占比 |
| ----- | ------------ | ---- | ----------------- |
| 09-22 | 3            | 10   | 23%               |
| 09-23 | 113          | 43   | 72%               |
| 09-24 | 27           | 1    | **96%**           |

从 23% → 72% → 96%，主备规则被模型接受。09-22 是 `EditAnchored` 刚引入、模型还不熟的一天。

## 2. 失败率：EditAnchored 明显更高

| 工具         | 成功 | 失败 | 失败率    |
| ------------ | ---- | ---- | --------- |
| EditAnchored | 105  | 38   | **26.6%** |
| Edit         | 251  | 22   | 8.1%      |

EditAnchored 的失败率是 Edit 的 **3.3 倍**。这是当前最需要解释的数字——但要注意两者不可直接比：EditAnchored 承担了「已读文件的常规编辑」这个主路径，Edit 退化成兜底（连续失败后才用），兜底路径本身面对的往往是更容易改的目标。

## 3. 原因分布：unserved + stale 占 64%

按消息文本分类（36 条失败）：

| 原因                          | 次数 | 占比 |
| ----------------------------- | ---- | ---- |
| `unserved`（锚点从未展示过）  | 13   | 36%  |
| `stale`（锚点曾展示，行已变） | 10   | 28%  |
| `malformed`（锚点格式错）     | 5    | 14%  |
| `ambiguous`（哈希多处命中）   | 3    | 8%   |
| `overlap`（批量区间重叠）     | 3    | 8%   |
| 其他                          | 2    | 6%   |

按天看有个明显变化：`stale` 10 条**全部**发生在 09-23，09-24 为 0。可能是自愈（整文件唯一哈希回退）在起作用，也可能是这两天改的文件类型不同（09-24 多在改 Java 业务代码，改动更集中）。

**原因码可用性已验证**：09-23 及以前所有失败都是 `code=1`（旧构建，原因不可分）；09-24 起出现 `code=2`（unserved）、`code=4`（ambiguous），与消息文本分类一致。也就是说「按 `toolName + error.context.code` 统计」这条口径现在真的能用了。

## 4. 降级规则：只被遵守 57%

连续失败 ≥2 次的片段共 12 个：

| 后续行为                      | 次数 |
| ----------------------------- | ---- |
| 改用 `Edit`（降级生效）       | 4    |
| 仍用 `EditAnchored`（未降级） | 3    |
| 该文件无后续编辑调用          | 5    |

在「确实还有下一次编辑」的 7 个片段里，降级 4 次 = **57%**。提示词规则有效但不强：模型有近一半时候会继续在同一个文件上硬试。

典型：`zcode-codes/t.ts` 连失 2 次后仍用 `EditAnchored`；`test/conversationTurnWorkSegmentsHistoryOpen.test.ts` 同样。

## 5. 往返

100 个文件、416 次编辑调用，平均每文件 4.2 次。这个数字本身看不出问题（多轮改同一文件是正常的），但结合 26.6% 的失败率，说明有相当一部分往返是在重试。

## 结论与建议（待决策，未实施）

按「先看数据再优化」的约定，这里只给判断，不动代码。

1. **`unserved` 是第一优先级（36%）**。锚点从未展示过，说明模型在没读、或读了但锚点没被 served 的情况下就用锚点。需要先分清是哪种：若是 Read 截断导致锚点没进 served，那是服务端问题；若是模型凭记忆编锚点，那是提示词问题。**下一步该做的是抽几条 `unserved` 的完整上下文（前一次 Read 的 offset/limit + 被拒锚点）来定性**，现在还不能下结论。

2. **降级规则值得从提示词升级为运行时约束（57% → 目标 100%）**。当前只有一句话，模型一半时候不照做。可以在 handler 侧对「同一文件已连续失败两次」的第三次调用直接拒绝并提示改用 `Edit`——代价是引入跨调用的文件级状态，需要先确认状态归属（现有 `readFileState` 是天然候选）。

3. **`malformed` 14% 是纯模型侧问题**，样本包括 `"0:DK0B"`（行号 0）、`"abc"`、`"not-an-anchor"`、`"44B6"`（缺行号）、`"KKXE"`（缺行号）。后两类是**只给了哈希、没给行号**，说明「行号:哈希」这个格式没被稳定记住。可以在拒绝消息里针对「只给哈希」这一种给更具体的纠正（现有消息只说了正确格式）。

4. **`overlap` 8% 值得看一眼**：批量编辑里区间重叠属于可以在调用前就判定的错误，拒绝消息若能指出是哪两条重叠，模型一次就能改对。

5. **不建议动的**：`stale` 占比高但 09-24 已归零，先观察；`ambiguous` 8% 属于哈希碰撞的正常水平。

### 3 处失败的全貌

| 时刻     | 原因                  | 具体                                                                                                                   |
| -------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 13:40:22 | `malformed`（code=1） | 13 个锚点**全部只给哈希、不给行号**（`H669`、`252V`…）；12 秒后补上行号（`31:H669`、`43:252V`…）用**同一批哈希**改成功 |
| 13:48:43 | inputSchema 校验失败  | 模型发出**空参数** `{}`；3 秒后正常调用成功                                                                            |
| 13:59:26 | `unserved`（code=2）  | 见下                                                                                                                   |

### `unserved` 定性：模型编造了哈希

这是上一节想弄清的那个问题，这个会话给了答案：

```
13:53:06  EditA index.ts  331:6QKE                     completed
13:58:31  Read  schema.ts offset=355 limit=45
13:59:18  Read  index.ts  offset=18  limit=40          ← 读了 18–57
13:59:26  EditA index.ts  240:41Q0, 332:ES7N           error: 240:41Q0 从未展示过
13:59:30  Read  index.ts  offset=240 limit=10          ← 补读
13:59:34  EditA index.ts  240:FJNV, 332:ES7N           completed
```

关键对比：**同一行的正确哈希是 `FJNV`，模型给的是 `41Q0`**。而 `332:ES7N`（它读过 316–361）是对的。

所以这里的 `unserved` 不是 Read 截断、也不是服务端没 serve，而是**模型对没读过的行猜了一个哈希**：行号 240 是对的（它知道要改哪一行），哈希是编的。补读之后立刻改对。

**结论：`unserved` 的主体是模型侧行为，不是服务端问题。** 现有拒绝消息 + 强制补读的组合有效——一次往返就自愈。

### 净成本

3 处失败**全部在下一步自愈**，没有一处演变成连续失败，所以降级规则在这个会话里根本没被触发。净成本 = 3 次多余调用 / 191 次 = **1.6%**。

这修正了上一节的一个判断：全局 26.6% 的失败率不等于 26.6% 的任务受阻——大部分在同一个回合内就被纠正了。**真正该看的是「失败是否引发连续失败/用户可见的卡顿」**，而这个会话是 0。
